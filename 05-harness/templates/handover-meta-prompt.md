# Tester Match 인수인계 문서 작성 프롬프트

> 사용법: 이 파일 전체를 리포 루트(`tester-match/`)에서 연 새 AI 세션에 그대로 붙여넣는다.
> 산출물은 `03-output/handover/` 에 생성된다. 서비스가 바뀔 때마다 다시 실행해 갱신한다.

---

## 1. 무엇을, 왜 만드는가

당신은 이 리포지토리를 처음 보는 상태에서 **인수인계 문서 세트**를 작성합니다.

독자는 이 서비스를 전혀 모르는 다른 AI 개발 에이전트(와 그 에이전트에게 일을 맡길 사람)입니다. 그 독자는 이 문서와 리포만 가지고 다음을 할 수 있어야 합니다.

- 첫날에 작은 기능 하나를 안전하게 수정·테스트·배포한다 (운영 중인 서비스를 망가뜨리지 않고).
- 돈이 오가는 흐름(결제·크레딧·보상·환급)을 건드릴 때 무엇이 위험한지 안다.
- "왜 이렇게 만들었는가"를 결정 기록까지 거슬러 올라가 설명한다.
- 투자자나 파트너에게 이 사업을 5분 안에 설명한다 — 누구의 어떤 문제를, 얼마를 받고, 어떤 비용 구조로 푸는지.
- 다음에 무엇을 해야 하는지, 지금 무엇이 반쯤 진행된 채 멈춰 있는지 안다.

운영자는 1인 창업자이고, 개발·운영·마케팅을 AI 에이전트와 함께 합니다. 그래서 이 문서는 사람용 요약서가 아니라 **다음 작업자가 실제로 일을 시작할 수 있는 작업 기반**이어야 합니다. 듣기 좋은 개요보다 정확한 사실, 함정, 미완료 상태가 더 가치 있습니다.

## 2. 배경 (출발점으로만 쓰고, 반드시 직접 확인할 것)

- 서비스: Tester Match — Google Play 비공개 테스트 요건(테스터 12명·14일)을 한국 인디 안드로이드 개발자끼리 품앗이로 해결하는 매칭 플랫폼. 무료 품앗이 위에 유료 "테스터 시트" 마켓(크레딧 보상·기프티콘 교환)을 얹는 중.
- 리포는 5레이어 구조다: `01-source/`(기획·결정, 읽기 전용) · `02-reference/` · `03-output/`(앱 코드 `app/`, DB 마이그레이션 `supabase/migrations/`, 정책) · `04-review/`(세션 기록) · `05-harness/`.
- 루트 문서: `CLAUDE.md`(작업 규칙·잠금 결정), `README.md`, `NEXT.md`(할 일), `WORKLOG.md`(일일 로그), `DEPLOY.md`(배포 절차·사고 이력). 결정 기록은 `01-source/decisions/ADR-*.md`.
- 서비스는 실사용자가 있는 **운영 중** 상태다.

**중요한 전제: 문서는 낡았을 수 있다.** 이 리포의 문서들은 서로 다른 시점에 쓰였고, 일부는 이미 사실과 다르다(예: 오래된 URL, 폐기된 계획, 바뀐 정책 수치). 문서끼리, 또는 문서와 코드가 어긋나면 **실제 코드와 DB 스키마가 진실**이다. 어긋남을 발견하면 조용히 고치지 말고 "문서 불일치" 목록에 기록한다 — 그 목록 자체가 다음 작업자에게 가장 유용한 정보 중 하나다.

## 3. 작업 원칙

1. **읽기 전용.** 이 작업 중에는 배포, 마이그레이션 적용, 운영 DB 쓰기, 외부 서비스 설정 변경, 결제·메일 발송을 하지 않는다. 만드는 것은 `03-output/handover/` 아래 문서뿐이다. 기존 파일은 수정하지 않는다.
2. **비밀값은 이름만.** 환경변수·시크릿은 이름, 용도, 설정 위치(로컬 파일 / 호스팅 대시보드 / CI 시크릿), 없을 때의 동작만 적는다. 값은 출력하지도 문서에 쓰지도 않는다. 값을 읽어야 하는 명령은 값이 화면에 나오지 않는 방식으로만 실행한다.
3. **개인정보 금지.** 운영 DB를 조회할 수 있다면 집계 수치만 쓴다(건수·합계·비율). 이메일·연락처·닉네임 등 개인 식별 정보는 문서에 넣지 않는다.
4. **근거를 남긴다.** 모든 사실 주장에는 출처를 붙인다 — 파일 경로(가능하면 줄 번호), 마이그레이션 파일명, 커밋 해시, 실행한 조회. 출처 없는 문장은 독자가 믿을 수 없다.
5. **확신 수준을 구분한다.** 각 항목에 `[검증]`(코드/DB/실행으로 직접 확인) · `[문서]`(문서에만 있고 코드로 확인 못 함) · `[추정]`(정황상 판단) 중 하나를 표시한다.
6. **모르면 지어내지 않는다.** 리포와 조회 가능한 데이터에서 답을 찾을 수 없는 것(실제 매출, 채널별 유입, 창업자의 의도, 외부 계정 상태 등)은 추측으로 메우지 말고 "창업자에게 물어볼 질문" 목록으로 보낸다.
7. **시점을 박는다.** 문서 머리에 작성 일시와 기준 커밋 해시를 적고, 빨리 변하는 수치·상태에는 "기준일"을 표시한다.
8. **기존 문서를 베끼지 않는다.** 원문이 정확하면 요약하고 링크한다. 인수인계 문서의 가치는 흩어진 사실의 통합·검증·현행화에 있다.

## 4. 조사 순서

범위가 넓으므로, 병렬로 일할 수 있는 하위 에이전트가 있다면 영역별(데이터 모델 / 기능·흐름 / 인프라·운영 / 사업·마케팅)로 나눠 맡기고 결과를 통합한다. 없으면 아래 순서로 진행한다.

**1단계 — 맥락 파악.** `CLAUDE.md` → `README.md` → `NEXT.md` → `WORKLOG.md` 전체 → `DEPLOY.md` → `01-source/decisions/` 의 모든 ADR(번호순) → `01-source/spec/`, `01-source/bp/`, `01-source/research/` → `03-output/policy/` → `04-review/history/`. 그리고 `git log` 전체 흐름과 현재 브랜치·미병합 브랜치·미커밋 변경.

**2단계 — 실제 상태 확인(진실의 원천).**
- 데이터: `03-output/supabase/migrations/` 를 시간순으로 전부 읽어 현재 스키마를 재구성한다. 조회 권한이 있으면 실제 DB 스키마와 대조한다.
- 코드: `03-output/app/src/app/`(페이지·API 라우트 전수), `src/lib/`(도메인 로직), `src/components/`, 테스트 파일, `package.json`, 런타임·빌드 설정.
- 운영: `.github/workflows/`(스케줄 작업), 호스팅 설정 파일, `.env.example`, `.claude/`(스킬·실행 설정).
- 리포 밖의 것: 문서와 코드에서 언급되는 모든 외부 시스템(호스팅, DB, 결제대행, 메일 발송, 구글 그룹/워크스페이스, 메신저 오픈채팅, 콘텐츠 자동화 파이프라인, 광고 등)을 찾아내 목록화한다. 접근할 수 없는 것은 "확인 불가"로 표시하고 확인 방법을 적는다.

**3단계 — 대조.** 1단계에서 읽은 주장 하나하나를 2단계의 사실과 맞춰 본다. 특히 다음은 문서에 적힌 대로 믿지 말고 **현재 상태를 직접 확인해서** 기록한다.
- 유료 기능이 실제로 누구에게 열려 있는가(공개 여부를 정하는 플래그·권한 검사).
- 결제 연동이 테스트 키 상태인가 실결제 상태인가. 결제대행사 심사 진행 상황.
- 알림 메일이 실제로 발송되는가(발신 도메인 검증 상태, 수신자 우회 설정).
- 스케줄 작업 각각이 실제로 등록·동작하는가, 마지막 실패 이력.
- 진행 중이거나 중단된 작업: 병합되지 않은 브랜치, 합의됐지만 구현되지 않은 설계(예: 보상 보류·구매자 확정·자동 확정, 결석 유예 규칙, 구매 전 유의사항 동의), 끝나지 않은 감사·리뷰.
- 사고 이력에서 나온 규칙(배포, 마이그레이션, 조회 제한, 외래키 임베드, 제약조건 동기화, 시간대 처리 등)이 지금도 유효한가.

**4단계 — 수치.** 가능하면 읽기 전용 집계로 현재 규모를 잰다: 회원 수, 앱 수(상태별), 매칭 수(상태별)와 완주율, 유료 주문·결제 건수, 크레딧 발행·사용·잔액 총량, 교환 신청. 조회할 수 없으면 그렇게 적고 질문 목록으로 보낸다.

## 5. 산출물

`03-output/handover/` 에 아래 파일을 만든다. 한 파일이 지나치게 길어지면 나눠도 되지만, `00-INDEX.md` 는 짧게 유지한다(처음 읽는 사람이 10분 안에 전체 그림과 "어디를 보면 되는지"를 얻는 것이 목표).

**00-INDEX.md — 시작점**
- 기준 일시·커밋, 한 문단 요약(무엇을 하는 서비스이고 지금 어느 단계인가)
- 현재 상태 스냅샷: 무엇이 운영 중 / 무엇이 관리자에게만 열림 / 무엇이 반쯤 만들어짐
- 지금 가장 급한 일 3~5개와 그 이유
- 나머지 문서 안내, 그리고 "이 작업을 하려면 이 문서부터" 식의 길잡이

**01-product-business.md — 제품과 사업**
- 해결하는 문제와 그 근거(플랫폼 정책 요건, 실제 사용자 행동 데이터), 대상 고객, 대안·경쟁과의 차이
- 사용자 유형별(앱 등록자 / 테스터 / 구매자 / 운영자) 핵심 여정
- 수익 모델 전체: 무료 영역과 유료 영역, 가격, 보상 구조, 결제 수수료, 건당 마진 계산식, 크레딧의 성격과 사용처, 과거에 시도했다 접은 수익원과 그 이유
- 비용 구조: 사용 중인 각 외부 서비스의 요금제·무료 한도·한도 도달 시 영향
- 핵심 지표의 정의와 현재값, 단계별 목표
- 가격·모델에 대한 잠금 결정과 변경 절차

**02-commercialization-legal.md — 사업화와 규제**
- 사업자 정보 공개 범위, 통신판매 관련 신고 의무와 현재 면제 근거·전환 기준
- 결제대행 계약·심사 상태, 실결제 전환에 필요한 단계
- 크레딧·교환이 걸리는 금융 규제 쟁점과 현재의 회피 설계, 세금 쟁점
- 플랫폼(앱 마켓) 정책상 금지선과 서비스가 지키는 가드레일
- 약관·개인정보·환불·크레딧 정책 각각의 핵심 조항과, 코드가 실제로 그 약속을 이행하는지 여부(약속과 구현의 차이는 반드시 표시)
- 미해결 법무 과제

**03-marketing-growth.md — 마케팅과 성장**
- 유입 채널 전부와 각 채널의 현재 운영 방식(커뮤니티 채팅방, 게시판 콘텐츠, 검색 노출, 알림, 가이드 콘텐츠 등)
- 콘텐츠 자동화 파이프라인: 무엇이 언제 무엇을 만들어 어디에 올리는가, 사람이 개입하는 지점, 현재 고장 난 부분
- 검색·공유 최적화의 구현 상태, 광고 수익화 시도 이력과 결과
- 핵심 메시지와 대상별 소구점, 약속해도 되는 것과 안 되는 것
- 전환 퍼널 각 단계와 측정 가능 여부, 가장 큰 이탈 지점
- 예정된 공지·출시 커뮤니케이션

**04-architecture-infra.md — 구조와 인프라**
- 기술 스택과 선택 이유, 런타임 제약(무엇이 안 되는가)
- 전체 구성도(텍스트 다이어그램): 사용자 → 호스팅 → DB/스토리지 → 외부 서비스
- 외부 시스템 대장: 각각의 용도, 설정 위치, 상태 확인 방법, 장애 시 영향, 접근 권한을 가진 주체
- 환경변수·시크릿 전체 목록(이름·용도·환경별 설정 위치·미설정 시 동작)
- 도메인·리다이렉트·프리뷰 환경의 제약
- 스케줄 작업 표: 이름, 주기(현지 시간 병기), 하는 일, 멱등 여부, 실패 시 영향과 복구 방법

**05-data-model.md — 데이터 모델**
- 모든 테이블: 목적, 컬럼(타입·제약·기본값), 관계, 인덱스, 행 수준 보안 정책, 트리거, DB 함수
- 테이블 간 관계도
- 상태값을 가진 컬럼마다 상태 전이도(누가, 어떤 조건에서 바꾸는가)
- 돈과 관련된 테이블(결제·주문·크레딧 원장·교환)의 불변식과 멱등성 장치
- 삭제 방식(소프트/하드)의 테이블별 차이, 스토리지 버킷과 객체 경로 규칙
- 마이그레이션 연표와 적용 절차, 이 DB에서 실제로 겪은 함정

**06-features-flows.md — 기능과 흐름**
- 기능 대장: 기능마다 사용자 관점 설명, 화면 경로, API 경로, 핵심 로직 파일, 사용 테이블, 테스트 유무, 상태(운영 / 제한 공개 / 휴면 / 폐기)
- 핵심 흐름의 단계별 서술(각 단계의 코드 위치 포함): 가입과 그룹 가입 / 앱 등록 / 매칭 참여 / 14일 체크인과 이탈 처리 / 신뢰도 / 유료 주문 → 결제 → 시트 충원 → 스크린샷 체크인 → 완주 → 보상 / 크레딧 사용과 교환 / 환불 / 관리자 업무
- 흐름마다: 실패 시 어떻게 되는가, 중복 요청에 안전한가, 알려진 사각지대
- 권한 모델: 역할, 관리자 판별 방식, 화면 가드와 API 가드의 위치

**07-dev-workflow.md — 개발과 운영 절차**

## 6. 서술 방식

- 한국어로 쓴다. 코드 식별자·경로·명령은 원문 그대로.
- 문장은 구체적으로. "빠르다", "안정적이다" 대신 수치와 조건을 쓴다.
- 표는 열거 가능한 사실(목록·대장)에만 쓰고, 이유와 맥락은 문장으로 쓴다.
- "무엇"만 적지 말고 "왜"를 적는다. 다음 작업자가 가장 자주 틀리는 지점은 이유를 모른 채 규칙만 따를 때다.
- 함정은 눈에 띄게: 과거에 실제로 사고가 났던 지점에는 무슨 일이 있었고 어떻게 피하는지 한 줄씩 붙인다.

## 7. 끝내기 전 자체 검증

1. 문서 전체에서 사실 주장 10개를 무작위로 골라 출처를 다시 열어 확인한다. 틀린 것이 나오면 같은 종류의 주장을 전부 재검토한다.
2. 다음 질문에 문서만 보고 답할 수 있는지 스스로 시험한다. 답이 안 나오면 문서를 보강한다.
   - 버튼 문구 하나를 바꿔 운영에 반영하려면 정확히 어떤 명령을 어떤 순서로 실행하는가? 하면 안 되는 것은?
   - 유료 주문 한 건이 결제부터 테스터 보상 지급까지 거치는 모든 테이블과 상태는?
   - 지금 이 서비스가 버는 돈의 경로와, 한 건당 남는 금액의 계산은?
   - 이 서비스가 오늘 갑자기 멈춘다면 가장 가능성 높은 원인 세 가지와 확인 순서는?
   - 지금 반쯤 만들어진 것은 무엇이고, 이어서 하려면 어디부터인가?
3. 비밀값·개인정보가 문서에 들어가지 않았는지 전체를 검색해 확인한다.
4. `[추정]` 과 `[문서]` 로 표시한 항목 수를 세어, 줄일 수 있는 것은 직접 확인해 `[검증]` 으로 올린다.
