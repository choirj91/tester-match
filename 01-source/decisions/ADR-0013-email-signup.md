# ADR-0013: 이메일 회원가입 추가 (Google 전용 로그인 개정)

- **상태**: Accepted (2026-10-03)
- **결정자**: nakjun
- **관련**: ADR-0004 (인증 전략 — Google 전용에서 개정), ADR-0012 (유료 시트)

## Context

- 결제대행사 가맹점 심사는 "상품 구매가 가능한 ID/비밀번호 테스트 계정"을 요구한다. Google 로그인만으로는 제공할 수 없다.
- 앱 등록자(구매자)에게 Google 계정을 강제할 이유는 없다. 반면 테스터는 Play 스토어·테스터 그룹 때문에 어차피 Google 계정이 필요하다.
- 운영 커뮤니티는 카카오톡 오픈채팅이라, 채팅방의 누가 어느 회원인지 연결할 식별자가 필요했다.

## Decision

1. **이메일·비밀번호 회원가입을 추가**한다. 가입 시 닉네임과 **카카오톡 닉네임**(오픈채팅 이름)을 필수로 받는다. Google 가입 회원은 프로필에서 선택 입력.
2. **이메일 인증 필수.** 서버가 인증 링크를 생성해 서비스 메일로 발송하고, 인증 전에는 로그인할 수 없다. 발송 실패 시 미인증 계정을 삭제해 재시도 가능하게 한다.
3. **유료 시트 참여는 Google 인증 계정만** 허용한다 (`PAID_SEAT_REQUIRES_GOOGLE`). 이메일 가입으로 계정을 쉽게 늘려 보상을 쌓는 경로를 막는다. 앱 등록·시트 구매는 이메일 계정도 가능.
4. 카카오톡 닉네임은 **공개 페이지에 노출하지 않는다** (운영자 식별·안내용).
5. 가입 화면은 인증 메일 발신 도메인이 검증될 때까지 닫아둔다 (`NEXT_PUBLIC_EMAIL_SIGNUP_ENABLED`). 이메일 **로그인** 폼은 즉시 제공한다 (심사 계정 등 운영자가 만든 계정용).
6. 공개 전 주문은 관리자 + 허용목록(`PAID_TESTERS_ORDER_ALLOWLIST`) 계정만 가능하며, 허용목록 계정의 주문은 **심사 모드**(시트 미개방, 급구·전 회원 알림 없음)로 처리한다.

## Consequences

- 인증 메일 발송에는 검증된 발신 도메인이 필요하다 (Resend 도메인 검증 — 선결 과제).
- 가입 엔드포인트는 임의 주소로 메일을 보내게 되므로, 가입을 열기 전에 봇 방지(Turnstile 등)가 필요하다.
- Supabase 의 이메일 가입 API 자체는 열려 있어, 우리 화면을 거치지 않은 가입은 카카오톡 닉네임 없이 생성될 수 있다 (공개 가입 차단은 Google 신규 가입까지 막으므로 보류).
- 비밀번호 재설정 흐름은 후속 과제.
- 개인정보처리방침 수집 항목에 비밀번호·카카오톡 닉네임을 추가했다.

## 보강 (2026-10-04) — 확인 후 연결, 비밀번호는 인증 단계에서, 사전등록 행은 Google 전용

### Context

공개 첫날, 운영자가 이메일로 가입하자 5월 일괄 등록으로 만들어진 다른 개발자의 사전등록 회원 행(앱 2개 포함)에 로그인이 연결됐다. 원인은 그 행의 이메일이 과거에 운영자 주소로 직접 수정돼 있었던 것으로, 연결 규칙(같은 이메일 + 아직 로그인 연결이 없는 행) 자체는 설계대로 동작했다. 조사와 독립 리뷰(보안·DB)에서 가입 흐름의 약점이 드러났다.

- 연결이 **이메일 확인 전**(계정 생성 시점)에 일어난다. 미확인 가입이 사전등록 행을 선점한다.
- `users.auth_user_id` 가 `on delete cascade` 라서, 사전등록 행을 선점한 미확인 계정을 지우면(메일 발송 실패 시 정리 등) 그 행과 앱까지 지워질 수 있다. 실제 발생은 없었다.
- **가입 단계에서 받은 비밀번호**는 가입한 사람의 것이다. 남의 주소로 가입해 두고 주인이 인증 메일을 누르면, 가입자가 정한 비밀번호로 그 계정(사전등록 행이 있으면 그 앱까지)에 들어갈 수 있다.
- 인증 링크가 열기만 해도(GET) 확정된다. 메일 보안 스캐너가 링크를 미리 열면 본인 모르게 인증된다.
- Google 여부 판별에 가입자가 직접 써넣을 수 있는 값(사용자 메타데이터의 `iss`)을 썼다.
- 로그인한 사용자가 공개 키로 자기 회원 행의 `email`·`google_id` 를 직접 고칠 수 있었다.

### Decision

1. 제공자와 무관하게 **이메일이 확인된 뒤에만** 회원 행을 만들거나 연결한다.
2. **사전등록 행은 Google 로그인만 가져간다.** 이메일·비밀번호 가입은 항상 새 행을 만들고, 사전등록 행이 있는 주소로는 가입을 받지 않는다(Google 로그인 안내).
3. **비밀번호는 가입 단계가 아니라 인증 단계에서 정한다.** 가입 폼은 이메일·닉네임·카카오톡 닉네임만 받고, 인증 전 계정은 아무도 모르는 임시 비밀번호로만 존재한다. 메일의 링크를 연 사람이 확인 화면에서 비밀번호를 정해야 가입이 끝난다.
4. 인증 메일의 링크는 인증 서버가 아니라 우리 사이트로 보낸다. 링크는 토큰을 수명 1시간의 HttpOnly 쿠키로 옮기기만 하고, 확인 화면의 양식을 제출해야(POST) 확정된다. 확인 화면 주소에는 토큰을 두지 않는다(전역 광고 스크립트 노출 방지). 확정 후 자동 로그인하지 않는다.
5. Google 여부는 서버만 쓸 수 있는 값(app metadata, `auth.identities`)으로만 판단한다.
6. 회원 행은 서버만 수정한다 — API 역할의 `UPDATE` 권한을 거둔다.
7. 받을 수 없는 주소(`@deleted.local`, `.invalid`, 도메인 없는 값)로는 메일을 보내지 않는다. 주인을 확인할 수 없는 사전등록 행은 이메일을 `.invalid` 주소로 봉인한다.
8. 사전등록 행에 연결될 때 약관·개인정보 동의 시각을 연결 시점으로 기록한다(일괄 등록 시각은 본인이 동의한 시각이 아니다).

### Consequences

- 확인되지 않은 가입은 회원 테이블에 흔적을 남기지 않는다. 미확인 계정을 지워도 다른 행이 딸려 지워지지 않는다.
- 남의 주소로 가입해도 얻는 것이 없다 — 비밀번호를 정하는 것은 메일을 받은 사람이다.
- 가입자는 메일에서 한 번 누르고, 확인 화면에서 비밀번호를 입력한다. 메일을 연 브라우저와 비밀번호를 입력하는 브라우저가 같아야 한다.
- 사전등록 주소의 주인이 Google 계정이 없으면 이메일로는 가입할 수 없다 — 운영자가 수동으로 처리한다.
- 사전등록 행의 이메일이 틀리면 엉뚱한 Google 계정에 연결되는 구조는 그대로다. 이메일을 직접 고칠 때는 닉네임·앱 주인과 맞는지 확인해야 한다 (2026-10-04 기준 주인 불명 3건: 397·398·556번).
- 남은 과제: 봇 방지(Turnstile), 가입 응답 단일화(주소 존재 여부 노출), 가입 시도 제한의 원자성·주소별 제한, 오래된 미확인 계정 정리, `auth_user_id` FK 를 `set null` 로 바꿀지, 비밀번호 재설정 흐름, `/api/auth/debug` 제거.
