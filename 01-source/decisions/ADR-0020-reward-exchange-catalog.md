# ADR-0020: 보상 교환 상품 카탈로그 — 상품별 크레딧

- **상태**: Proposed (2026-10-08 운영자 요청 — 정책 문구 승인·운영 DB 마이그레이션 뒤 배포 시 Accepted)
- **결정자**: nakjun
- **관련**: ADR-0012 (기프티콘 교환 규칙), ADR-0014 (크레딧 적립원 단일화), ADR-0017 (크레딧 보상 전용·PG 심사 표현 규칙)
- **개정**: ADR-0017 Decision 4 의 "5,000 크레딧 단위"

## Context

- 지금까지 교환은 금액을 고르는 방식이었다: 5,000 크레딧부터 5,000 단위, 1회 최대 50,000. 기프티콘은 신청 메모에 브랜드를 적고 운영자가 맞춰 보냈다.
- 운영자 요청(2026-10-08): 회원이 **구체적인 상품**(네이버페이 포인트 쿠폰, 커피 기프티콘)을 고르고, 상품마다 크레딧이 정해져 있게 한다. 예: 스타벅스 카페 아메리카노 T = 그 상품 정가만큼의 크레딧.
- KG이니시스 전자결제 계약 심사 중이다(ADR-0017). 크레딧 화면은 "구매·충전·환전·현금·환급·판매·결제"로 읽히면 안 된다. 상품 목록이 쇼핑몰처럼 보이면 상품권 판매로 오해받을 수 있다.
- 상품 사진과 브랜드 로고는 각 회사의 저작물·상표다. 사용 허락이 없다.
- 1회 50,000 크레딧 상한은 기타소득 과세최저한(건당 5만 원) 안에 두려는 것이다 — 그대로 둔다.

## Decision

1. **상품 카탈로그**: 교환은 앱 코드 한 곳(`lib/rewards.ts` 의 `REWARD_ITEMS`)에 정의한 상품으로만 한다. 상품마다 바뀌지 않는 코드(`npay_5000`, `starbucks_americano_t` 등), 종류(`gifticon` | `naver_points`), 브랜드, 이름, **1개당 크레딧**, 아이콘, 발송 안내가 있다. 상품 크레딧 = 상품 정가(원)와 같은 수 (1 크레딧 = 1원 상당). 정가는 확인한 날짜와 출처를 코드 주석에 남기고, 확인하지 못한 상품은 싣지 않는다.

   | 코드 | 상품 | 크레딧 |
   |---|---|---|
   | `compose_americano_hot` | 컴포즈커피 아메리카노 (HOT) | 1,500 |
   | `mega_americano_hot` | 메가MGC커피 (HOT)아메리카노 | 1,700 |
   | `starbucks_americano_t` | 스타벅스 카페 아메리카노 T | 4,700 |
   | `npay_5000` | 네이버페이 포인트 5,000원권 | 5,000 |
   | `npay_10000` | 네이버페이 포인트 10,000원권 | 10,000 |

2. **신청 단위**: 한 번에 **상품 1종 × 수량 1~10**, 합계 **최대 50,000 크레딧**. 5,000 크레딧 단위·최소 5,000 규칙은 없앤다 (가장 싼 상품이 사실상 최소). 서버는 상품 코드로 크레딧을 계산한다 — 클라이언트가 보낸 금액·종류는 버린다.
3. **기존 안전장치 유지**: 유료 시트 완주 적립분만 교환(`ledger_append` 의 `p_cap_redeemable`), 신청 즉시 차감·거절 시 복구, 처리 대기 신청은 회원당 1건, 휴대폰 번호는 해시로 한 계정에만, 운영자 수동 발송·영업일 3일. 바뀌는 것은 금액을 정하는 방법뿐이다.
4. **기록**: `credit_redemptions` 에 `item_code`, `quantity` 를 더한다 (마이그레이션 `20261008000001_redemption_item.sql`). 2026-10-08 전 신청은 둘 다 null 이고 관리자·내역 화면은 종류·금액으로 보여 준다. 백필하지 않는다. 상품 목록은 배포로 바뀌므로 DB 에 값 목록 CHECK·FK 를 두지 않는다 (형식·수량 범위·둘이 함께 있는지만 검사).
5. **표현**: 교환이지 구매가 아니다. 크레딧 맥락에서 "보상 교환·교환 신청·교환하기"를 쓰고, 크레딧 수 옆에 ₩·원을 붙이지 않는다 ("4,700 크레딧"). 상품 이름에는 권면 금액이 들어갈 수 있다 ("네이버페이 포인트 5,000원권").
6. **이미지 없음**: 상품 카드는 lucide 아이콘(커피잔·지갑)과 글자만 쓴다. 상품 사진·브랜드 로고는 싣지 않는다. 카탈로그 타입에 `imageUrl` 자리만 두고 비워 둔다 — 사용 허락을 받은 이미지가 생기면 그때 채운다. 브랜드명은 상품을 가리키는 글자로만 쓰고 "각 회사의 상표" 문구를 둔다.
7. **수동 발송 그대로**: 제휴·API 연동 없이 운영자가 상품을 마련해 휴대폰으로 보낸다. 관리자 화면은 "상품 × 수량"을 보여 준다.

## Why

- **회원 입장**: "5,000 크레딧 → 기프티콘(브랜드 메모)"보다 "스타벅스 아메리카노 T 4,700 크레딧"이 무엇을 받는지 분명하다. 가장 싼 상품이 1,500 크레딧이라 시트 3개 완주(시트당 최대 600, 출시 보너스 포함 700)로 첫 교환이 된다 (이전 최소 5,000 은 8~9개).
- **금액 신뢰**: 금액을 서버가 카탈로그에서 계산하므로 클라이언트 조작으로 다른 금액을 차감할 수 없다. 상품 코드가 행에 남아 운영자가 무엇을 보내야 하는지 메모를 해석하지 않아도 된다.
- **심사 표현**: 상품 목록이 있어도 결제 경로가 없고(크레딧은 구매 불가), 문구가 "교환"으로만 쓰여 상품권 판매로 읽히지 않는다.
- **상표·저작권**: 사진·로고 없이 글자와 일반 아이콘만 쓰면 허락 없이 제3자 이미지를 싣는 문제가 없다.

## Consequences

- **배포 순서**: 운영 DB 에 마이그레이션 `20261008000001` 을 먼저 적용한 뒤 앱을 배포한다. 순서가 바뀌면 `/credits` 내역과 관리자 목록 조회(`item_code` 열)가 실패하고, 신청 insert 가 실패해 즉시 복구된다.
- **정책 문구 개정**: 크레딧 운영 정책 제3조의 "5,000 크레딧부터 5,000 크레딧 단위" 문장을 "교환 상품별로 정한 크레딧, 1회 최대 50,000 크레딧"으로 바꾼다. 운영자 승인 뒤 시행한다. 시행일 표기는 이 ADR 에서 바꾸지 않는다.
- **가격 관리**: 브랜드 정가가 바뀌면 `REWARD_ITEMS` 의 크레딧과 출처 주석을 고쳐 배포한다. 이미 접수된 신청은 신청 때 차감한 크레딧 그대로 처리한다. 상품을 빼더라도 코드는 재사용하지 않는다 (이전 신청 표시).
- **운영 부담**: 1,500~1,700 크레딧 상품은 건수가 늘 수 있다. 처리 대기 1건 규칙은 그대로라 회원당 동시 1건이다. 건수가 운영을 넘으면 최소 신청 크레딧을 다시 두거나 자동 발송을 검토한다.
- 이디야커피 아메리카노는 2025-12-16 기본 사이즈 변경 뒤 가격을 확인하지 못해 뺐다. 확인되면 추가한다.
